# Stemory Blooms project audit

18 October 2026

Stemory Blooms has the main pieces of a store, but the connections between them are unreliable. The most urgent work is to protect customer information and make orders, stock, discounts, delivery, and money agree. A visual redesign should follow those repairs and make the daily workflows easier to use.

This audit records **43 findings: 4 P0, 27 P1, and 12 P2**. P0 means urgent security or order-integrity work before reopening or expanding sales. P1 means a broken core workflow or a substantial operational risk. P2 means an important usability, completeness, or maintainability improvement. Priorities express impact; they do not imply that an exploit or financial loss has been observed.

The companion [implementation plan][plan] groups the findings into releases, specifies the proposed admin experience, and gives acceptance criteria.

## Scope and verification

The review covered the storefront, cart, product details, custom builder, checkout, tracking, account, receipts, public APIs, admin pages and actions, authentication, database schema and migrations, shared components, delivery integration, email, reporting, and repository checks.

Code findings below are confirmed from the repository unless explicitly described as a design recommendation. The local browser initially showed maintenance mode and redirected admin access to Clerk. After sign-in completed, the existing administrator session allowed inspection of the main admin screens and the built-in storefront preview without changing the public site mode. Desktop checks used 1440px; selected mobile flows used 390px. Contrast measurements, screen-reader testing, the remaining breakpoint matrix, and mutation-based integration tests still require isolated test data. Production configuration, backup restoration, courier contracts, and actual email delivery were not verified.

No orders, stock, roles, site modes, or external communications were changed for the audit. One temporary local cart item was added to inspect checkout and removed afterward. The deliverables are project documentation.

## Urgent security and order integrity

### F01 P0 Product quick edits lack authorization

`quickUpdateProduct` changes prices, finished stock, material quantities, and builder stock without calling `assertAdmin`. The proxy checks that `/admin` visitors are signed in; the admin layout checks their role, but a layout is not an authorization boundary for a directly invoked server action. Other product actions correctly check the role. [Product mutations][product-actions], [proxy][proxy], [admin layout][admin-layout].

**Fix:** require authorization inside every sensitive action or service entry point and validate its input. Test anonymous, customer, and admin requests independently of the UI. Also make role authority consistent: the current synchronization can preserve admin privileges after removing Clerk metadata, or restore privileges from metadata after a database-only demotion. Protect against removing the final administrator. [User synchronization][user-sync], [role changes][user-actions]. Exploitability was not tested by changing real data.

### F02 P0 Receipts expose customer information by order number

`/receipt/[orderNumber]` reads an order, its customer, and its items without authentication, an ownership check, or a secret access token. It sends the full order and customer objects to a client component. The route is outside the proxy's protected routes. Guessable order numbers compound the exposure. [Receipt page][receipt], [proxy][proxy].

**Fix:** use authenticated ownership for account receipts and an unguessable, revocable token for guest receipts. Return only necessary receipt fields, and send private caching and indexing directives. Merely hiding the URL from search engines does not protect it.

### F03 P0 Orders commit when stock deduction fails

Website and assisted checkout insert orders and items, then run conditional stock updates. Neither verifies that the updates affected the required rows. An out-of-stock or concurrent purchase can therefore still produce a successful order without reducing stock. Website checkout also does not require the product to be published or available. [Order API][orders-api], [assisted orders][order-actions].

**Fix:** aggregate demand by stock item, reserve or deduct atomically, require every deduction to succeed, and roll back the complete order otherwise. Recheck eligibility inside the same operation. Apply the same service to website, assisted, and custom orders. Include a concurrency test for the final unit.

### F04 P0 Custom configuration and numeric inputs are not bounded

The checkout contract allows arbitrary configuration and non-integer item quantities. The server casts component quantities to numbers without validating positivity, bounds, stock, or component availability, and silently ignores unknown component IDs when pricing. A negative quantity for a known component can lower the price and reverse the stock deduction. Fractional quantities can reach integer database columns and fail late. [Checkout contract][contracts], [order API][orders-api].

**Fix:** separate catalog items from custom items in a strict schema. Validate bounded integer quantities, known available components, supported component types, required choices, message length, and total request size. Exclude text metadata from the quantity map. Reject invalid requests before touching customer, stock, or money records.

## Checkout and customer data

### F05 P1 Custom bouquets cannot complete the normal checkout path

The builder stores a synthetic ID such as `custom-…`. Checkout forwards every cart item's ID as `productId`. The server then looks for that synthetic ID in the product table and returns “Product not found,” before reaching its custom-pricing branch. [Builder cart creation][builder-flow], [checkout mapping][checkout], [order API][orders-api].

**Fix:** give each cart item a local `cartLineId` and a separate item type. Send a real `productId` only for catalog lines. Preserve selections and card text through ordering, receipts, and production instructions. Verify mixed carts as well as custom-only carts.

### F06 P1 Custom prices differ between preview and server

The storefront and assisted-order product loader show wrapping and cards at zero, but their server handlers charge the component's stored `unitPrice`. This creates a mismatch whenever those stored prices are nonzero. The builder also puts `cardMessage` inside the component-quantity object, which stock mutations iterate as if all values were quantities. [Builder data][builder-page], [assisted form data][assisted-page], [order API][orders-api], [order mutations][order-actions].

**Fix:** establish one pricing policy for included packaging, extra cards, and the base fee. Use one server quote for both previews and committed totals. Store card text separately from component quantities.

### F07 P1 Idempotency does not recover retries

The API requires and stores a unique idempotency key but does not return an existing order for a replay. Checkout generates a new key on each submission. A lost response can lead to another order; replaying the same key instead raises a database error. An admin-notification insertion after the order commits can also turn a successful purchase into a 500 response. [Checkout submission][checkout], [order API][orders-api], [order schema][schema].

**Fix:** persist one key for a checkout attempt, bind it to the request payload, and return the original result on an identical replay. Reject conflicting reuse. Keep nonessential notification failures out of the order response and queue notifications within the transaction.

### F08 P1 Order numbers repeat

Both order entry points use the last six digits of a millisecond timestamp, with `ORD` or `AST` prefixes. The numeric space repeats every 1,000,000 milliseconds, or 16 minutes 40 seconds, and simultaneous submissions can collide. A unique database constraint then fails the purchase. [Order API][orders-api], [assisted orders][order-actions], [unique constraints][schema].

**Fix:** use a database sequence or a sufficiently large random reference with collision handling. Keep human-readable order references separate from guest access secrets.

### F09 P1 Discounts can be applied without consuming their balance or allowance

Promo and gift-card records are read before conditional updates, and the update results are ignored. Two concurrent requests can both receive the benefit even when only one consumption succeeds. Orders store a combined discount but no redemption link or ledger for promo and gift-card usage; cancellation has no corresponding restoration path. [Order API][orders-api], [assisted orders][order-actions], [discount tables][schema].

**Fix:** consume benefits atomically and verify success. Record promo discounts and gift-card tender separately, with redemption and reversal entries linked to the order. Use a cryptographically secure gift-code generator instead of the form's short `Math.random` code. Preserve balances under concurrent use and cancellation.

### F10 P1 Maintenance and waitlist modes do not stop order creation

The storefront layout replaces the public interface in maintenance or waitlist mode. The order API reads settings only to get the builder fee and continues accepting orders in either mode. `DRAFT` is accepted by settings but receives no equivalent storefront gate. [Storefront layout][store-layout], [order API][orders-api], [settings actions][settings-actions].

**Fix:** define the behavior of each mode once and enforce it at both read and write boundaries. An admin preview should be explicit and must not silently reopen public checkout.

### F11 P1 Delivery price is not securely tied to the destination

The field named `deliveryCompanyId` actually carries a delivery-zone ID. The API accepts any matching zone without checking that it is active or matches the submitted city. Missing or invalid selections fall back to the first active zone or 50 MAD. Checkout displays zero until a zone resolves. [Checkout contract][contracts], [checkout][checkout], [order API][orders-api].

**Fix:** require an active `deliveryZoneId`, derive or validate the destination from it, and reject unsupported destinations. Use explicit pickup or hand-delivery modes. Store the zone, fee, and delivery estimate on the order. Show an actionable loading failure and retry when cities cannot load.

### F12 P1 Customer matching conflicts between sales channels

Website checkout upserts on email; assisted orders upsert on phone. Both columns are unique. A repeat customer using the same phone with a different email can cause the website insert to fail, while another existing email can cause the assisted upsert to fail. Email casing and Moroccan phone formatting are not normalized consistently. [Order API][orders-api], [assisted orders][order-actions], [customer constraints][schema].

**Fix:** normalize contact identifiers, resolve matches consistently, and handle conflicting identities explicitly. Do not silently merge people solely because an unverified checkout supplied somebody else's email. Define safe linking for signed-in and guest orders.

### F13 P1 Historical orders depend on a mutable customer profile

Orders retain the delivery address but not an independent contact-name, email, and phone snapshot. Receipts and courier submission use the current linked customer. A subsequent checkout can overwrite the name or phone shown for an earlier order. Product names also come from client input in website checkout rather than the trusted product record. [Order API][orders-api], [receipt page][receipt], [courier push][order-actions].

**Fix:** snapshot buyer, recipient, address, item name, configuration, price, and accepted policy version at purchase. Use those snapshots for fulfillment and receipts. Keep profile updates separate from historical order data.

## Orders inventory delivery and finances

### F14 P1 Order transitions and cancellation are inconsistent

The orders action restocks and changes status in separate writes, accepts arbitrary status strings, and reads status without locking. Concurrent cancellation can restock twice. Reopening a cancellation clamps stock to zero instead of proving stock exists. The deliveries action changes status through a different path that omits restocking and courier synchronization. History tables exist but these actions do not populate them. [Order mutations][order-actions], [delivery mutations][delivery-actions], [history schema][schema].

**Fix:** define allowed transitions and one transactional transition service. Record actor, reason, previous and next state, inventory movement, and relevant money reversal. Make repeated transitions harmless. Keep `CONFIRMED`, production, delivery, and completion semantics consistent across every screen and tracking.

### F15 P1 Permanent order deletion can damage inventory and history

Deleting any non-cancelled order restores its stock, including delivered orders. Item deletion, stock restoration, related deletion, and order deletion are not atomic. Existing receipt, adjustment, or history foreign keys can stop the final deletion after earlier changes have already succeeded. [Deletion action][order-actions], [order relationships][schema].

**Fix:** archive normal business records and use explicit cancellation or return workflows for stock and money. Reserve permanent deletion for a controlled maintenance process with referential checks and a transaction. Preserve the audit trail.

### F16 P1 Revenue and profit do not represent collected money

Finances sums all orders, including cancelled and unpaid orders. Dashboard totals exclude cancellations, but its seven-day chart and top products include them; the ranking also groups packaging fees and component lines as bouquets, observed in the browser. Reports use another calculation. Payment status is displayed, but there is no implemented payment-reconciliation action using the history model. Orders and detail pages label merchandise value excluding delivery as “Total”; the payment method shows the sales source. All nine browser-listed orders appeared completed/delivered with `PENDING_COD`, without establishing whether their cash was actually collected. [Finances][finances], [dashboard][dashboard], [reports][reports], [orders list][orders-page], [order detail][order-detail].

**Fix:** show booked sales, cancelled value, delivered value, cash collected, courier remittance pending, gift-card tender, delivery charges, refunds, and expenses separately. Use one documented calculation across screens. Show merchandise subtotal, delivery fee, and amount to collect with explicit labels. Record payment events and reconcile COD remittances. Treat profit as provisional until cost and collection accounting are reliable.

### F17 P1 Gift-card creation is broken

The form submits `initialValue`; the action reads `initialBalance`. Creation therefore fails required balance validation. Its active toggle submits `true` or `false`, while the action expects `on`, so that toggle would save false after the balance mismatch is fixed. Sender and recipient fields have no corresponding persistence or delivery behavior. [Gift-card form][gift-form], [gift-card action][promo-actions], [schema][schema].

**Fix:** align the form, schema, server validation, and edit defaults. Implement recipient delivery only if the product offers it; otherwise remove unsupported fields. Test actual form submissions, not just the action in isolation.

### F18 P2 Promotion rules shown in the UI are not enforced

The form offers minimum spend, but the action and table have no such rule. Percentage values are not bounded to 100, and server validation does not restrict supported types or positive values consistently. [Promotion form][promo-form], [promotion mutations][promo-actions], [schema][schema].

**Fix:** support and enforce minimum spend and any advertised expiry, eligibility, and stacking rules, or remove the controls. Validate and normalize codes and rule ranges on the server.

### F19 P2 Supplier selection is discarded when adding materials

The material modal submits `supplierId`, but `saveMaterial` never reads or stores it. The inventory screen has a supplier column and loads supplier choices, creating the impression that the association will be saved. [Material modal][material-modal], [material mutations][material-actions].

**Fix:** validate and persist the supplier association on create and edit, refresh the relation after saving, and provide a visible path to supplier management.

### F20 P1 Product editing also changes manufacturing stock

Saving a product or builder component deducts raw materials based on finished stock and its recipe. Quick stock adjustments apply the same mechanism. These paths can write negative material or component quantities and use read-then-write balances vulnerable to concurrent edits. Reducing finished stock manually can return ingredients as if a completed bouquet had been disassembled. An “Auto-Deduct” backfill is exposed as a routine inventory tool. Browser inspection confirmed two negative wrapping balances, −6 and −8; it did not establish which action produced them. [Product mutations][product-actions], [builder mutations][builder-actions], [inventory client][inventory-client].

**Fix:** separate editing a recipe, manufacturing stock, reserving for a sale, writing off damage, and correcting a counted balance. Record reasoned stock movements with atomic balance checks. The current backfill has no applied marker and deducts the same stock again on each run; remove it from routine operations and audit its effects before any rerun. Decide explicitly which products are ready-made and which are made to order.

### F21 P1 Restocking and expense recording can disagree

Material creation/restock writes inventory and its expense separately. Restock reads the old quantity and replaces it with an absolute value, so concurrent purchases can lose updates. Inline stock edits bypass purchase accounting. Amounts can be negative at the server boundary; several cost paths round MAD amounts to whole dirhams while expenses allow decimals. [Material mutations][material-actions], [numeric parsers][form-values], [expense mutations][finance-actions].

**Fix:** create a purchase/restock transaction with atomic quantity increments, purchase unit cost, expense record, and movement history. Separate stock correction from purchase. Choose one documented money unit and migrate safely; validate whole-unit quantities independently of money decimals.

### F22 P2 Inventory updates leave stale or false UI state

Inline edits and restocks optimistically change client data without rollback. Several material actions revalidate `/admin/materials` but omit the active `/admin/inventory` screen. The client copies incoming data into state without synchronizing subsequent server updates. Failed writes can look saved and successful changes can leave summary cards stale. [Inventory client][inventory-client], [material mutations][material-actions].

**Fix:** reconcile against returned server state, roll back failed optimistic changes, invalidate affected lists and summaries, and show saving/failed/saved state per operation.

### F23 P1 Delivery handoff and courier submission are separate incomplete flows

The deliveries page loads only the first delivery company and omits customer/handoff relations. In the browser, cards therefore showed Guest and missing contact/reference fields despite corresponding records having customer details in Orders. Delivered orders still offered Dispatch. A local handoff sets `SHIPPED` without performing the courier push; the orders screen has a separate push that only sets a boolean. Handoff writes are not transactional. Courier calls have no explicit timeout, durable retry, or concurrent-submit guard, and completion updates use a detached promise. Tracking displays live courier text alongside independently maintained local status. [Delivery page][deliveries-page], [delivery mutations][delivery-actions], [courier push][order-actions], [courier integration][infinidis].

**Fix:** provide one dispatch flow: eligible order, active carrier selection, amount to collect, submit, acknowledgement/reference, then handoff. Store attempts and external references, make retries idempotent, and define how courier updates reconcile with local states. Validate the actual carrier API requirements before changing its authentication or status mapping; the provider contract was not verified here.

### F24 P1 Customer confirmations and background delivery are incomplete

Order emails are addressed only to the store inbox, using a Resend onboarding sender. The customer email is embedded in the template but is not a recipient. Provider-returned errors are not checked, and a database notification failure after purchase commit can make checkout report failure. A notification outbox table exists without an implemented worker in the application. [Order API][orders-api], [assisted orders][order-actions], [outbox schema][schema].

**Fix:** configure and verify the sender, send separate buyer and merchant messages, and record delivery outcomes. Queue work durably with bounded retries and an admin resend action. External-message failures must not invalidate an already committed order. Do not automate the success screen's promised WhatsApp contact until a real workflow exists.

## Admin usability and missing workflows

### F25 P1 Mobile admin navigation cannot reach most sections

At 480px and below, the sidebar disappears and the bottom bar exposes only Dashboard, Orders, Products, Settings, and a site-mode switch. There is no full navigation drawer. Inventory, finances, custom builder, customers, messages, and other sections lose their normal navigation entry. Several pages also use fixed multi-column layouts, including the order-detail `1fr 350px` grid and four-column inventory summary. At 390px, the order main area measured 390px while its contents measured 788px, putting customer and delivery details off-screen; inventory summary labels and amounts visibly overlapped. Large stacked summary cards also pushed dashboard queues and the order list far below the initial viewport. [Admin shell][admin-shell], [responsive CSS][admin-css], [order detail][order-detail], [inventory page][inventory-page].

**Fix:** add a complete mobile menu, retain quick links for frequent work, and make page layouts responsive. Make the store-mode control accessible from settings rather than consuming a scarce primary-navigation slot. Validate at 360, 390, 768, 1024, and 1440px.

### F26 P2 Admin navigation hides work and gives weak orientation

Reviews and Suppliers have pages but no entries in the sidebar. Section headings replace the page name in the top bar, the initial expanded section does not follow later route changes, and `/admin/orders/new` also matches the Orders entry. Collapsed groups use height and overflow without removing hidden links from keyboard navigation. [Admin shell][admin-shell].

**Fix:** organize navigation around tasks, expose every supported area, add exact page titles and breadcrumbs, use precise active matching, and prevent focus entering closed groups. Provide a pending-review count and a clear route to suppliers. Simplify duplicate routes/components after their replacement workflows are verified.

### F27 P1 The order list is inadequate as a daily workspace

Orders loads the entire history and relations, with no search, date/source/status filtering, pagination, or bulk work. Status is primarily represented by an immediate dropdown mutation rather than a clear fulfillment column and next action. `CONFIRMED` is not a dropdown option, while `DELIVERED` is locally mapped to `COMPLETED`. Errors can leave the action busy because it lacks `try/finally`. Custom component selections and card text are not presented as production instructions in order detail. [Orders page][orders-page], [row actions][order-ui], [order detail][order-detail].

**Fix:** create saved status views, server search and pagination, clear payment/delivery badges, safe next-step actions, and a full order detail timeline. Show custom recipe, card text, buyer/recipient, merchandise value, delivery, amount due, and integration errors. Protect destructive or irreversible transitions with a reason and confirmation.

### F28 P2 Custom-order drafts are a placeholder

The custom-order screen lists `DraftOrder` rows and renders a View button with no handler or link. No draft creation or conversion path uses that model elsewhere in the application. Assisted entry does not provide a durable draft workflow. [Custom-order page][custom-orders], [assisted form][assisted-form].

**Fix:** make “custom order” an order type with real recipe detail, and add draft creation, resume, quote, and conversion if staff need them. Keep drafts out of revenue and inventory commitment until confirmed. Remove placeholder navigation while its replacement is incomplete.

### F29 P1 The content editor does not update the advertised storefront content

Marketing offers generic content blocks for hero text, FAQs, care notes, and campaigns. The application writes and lists `ContentBlock` records, but storefront components do not read them. Saving a block therefore does not change the advertised public content. It also exposes raw JSON/copy to a nontechnical operator. [Content screen][content-page], [content mutations][content-actions], [homepage][home-client].

**Fix:** define supported editable content types, connect them to actual rendering, and provide structured fields with draft preview and publish. If a content type is unsupported, remove its implied capability.

### F30 P2 Marketing combines creation with lists that cannot manage existing records

The marketing page renders blank creation forms and tables but does not pass existing promo or gift-card records into edit forms, or expose the existing delete/disable controls there. This prevents ordinary management of issued codes. The separate Promotions route simply redirects back. [Content screen][content-page], [promotion mutations][promo-actions].

**Fix:** provide searchable lists with edit, disable, usage/redemption history, and expiry information. Prefer disabling used benefits to deleting their history. Group announcements, promotions, and actual content editing into clear subpages.

## Storefront experience accessibility and trust

### F31 P1 Catalog cards allow unavailable items into the cart

The shop query selects published products but drops stock and availability from card props. `ProductCard` always exposes Add. Product detail disables Add for `isAvailable`, but its quantity control has no stock cap. The public products API returns every row and field, including unpublished products. Search only filters the fully fetched catalog by name/description, with no category, price, or occasion filters. No-match results use a sold-out message and link to `/waitlist`, a route that does not exist. [Shop][shop], [product card][product-card], [product detail client][pdp], [public products API][products-api].

**Fix:** share stock and availability rules across cards, details, cart, and server checkout; support an explicit made-to-order state where relevant. Restrict the public catalog API to published products and an explicit public field set. Add useful browse filters and sorting, and distinguish zero results, an empty catalog, and a loading failure. Replace broken waitlist links with a real destination.

### F32 P1 Cart totals and discount feedback can disagree with the final charge

Cart prices persist locally while the server reprices at submission without a customer-visible quote comparison. Discount amounts stay in component state and are not recalculated when the cart changes. Editing or clearing an applied code resets its displayed amount but does not clear the submitted form code, so an apparently removed code can still be applied or rejected. The server uses `salePrice ?? basePrice` while storefront pricing checks the sale-enabled flag. [Cart store][cart], [checkout][checkout], [order API][orders-api], [product detail][pdp].

**Fix:** request a current quote after cart, destination, or code changes, show any price changes before placing the order, and model applied benefits in one state. Require confirmation of the final amount. Use the same sale rule and show both packaging and delivery estimates consistently.

### F33 P1 Custom controls lack keyboard and accessibility behavior

The shared admin dropdown and toggle use clickable divs without focusability, keyboard handling, or selected/expanded roles. Checkout's city options rely on mouse events; policy checkboxes use `display:none`, removing them from keyboard focus. Cart/search overlays and confirmation modals lack a complete dialog focus lifecycle. Several icon buttons have no accessible name, and a product card nests a button inside a link. [Dropdown][dropdown], [toggle][toggle], [checkout][checkout], [header/cart][header], [confirmation modal][confirm], [product card][product-card].

**Fix:** preserve the custom visual style while using semantic buttons, styled real inputs, proper combobox/listbox patterns, and accessible dialogs. Provide Arrow/Enter/Escape behavior, focus trapping and restoration, visible focus, screen-reader labels, and reduced-motion support. This can respect the project's preference against browser-default visual controls.

### F34 P2 Failures are hidden or misreported

Shop catches a database failure and displays the empty/sold-out state. Several admin forms discard the server result, mutations use generic failures, optimistic actions do not roll back, and there are no route-specific error boundaries for the main operational areas. [Shop][shop], [settings screen][settings-page], [inventory client][inventory-client], [order UI][order-ui].

**Fix:** define distinct loading, empty, success, validation failure, permission failure, conflict, and service-unavailable states. Keep form values on failure and provide retry and field-level feedback. Log a request reference without exposing raw database errors to customers.

### F35 P2 The customer account is difficult to reach and incomplete

The signed-in header renders a Clerk user button but no explicit My Orders link. The account finds customers using the first email address rather than an explicit verified ownership relation. Order history has no detail/receipt/tracking links. Saved-address copy says addresses can be added at checkout, but checkout does not write to the address table. Customer admin is also a read-only list without profile/order navigation or safe contact correction. [Auth slot][auth-slot], [account][account], [order API][orders-api], [customer screen][customers-client].

**Fix:** link My Orders visibly, define verified account-to-customer ownership, add order detail and secure receipt links, and implement address management or remove the promise. Add customer detail with purchase history and controlled profile edits. Guest checkout should remain available.

### F36 P2 Checkout policies and service promises are incomplete

Checkout requires four separate policy acceptances but does not link to their full text. Terms, privacy, and standalone COD policy routes are absent. Shipping and return pages provide broad language without firm coverage, charges, time windows, or a clear resolution process. The footer WhatsApp link points to `#`, and success copy promises WhatsApp follow-up without an implemented automation. [Checkout][checkout], [shipping][shipping], [returns][returns], [footer][footer], [success screen][success].

**Fix:** publish accurate business policies and link them at the decision point. Combine production and destination delivery estimates, expose a working support channel, and distinguish order received from staff confirmed. Simplify acceptance only after deciding the actual business requirements; this audit makes no legal-compliance determination.

### F37 P1 Public submissions lack abuse controls and complete validation

There is no application-level rate limit in order creation, tracking, contact, review, waitlist, or discount validation. Reviews accept ratings outside 1–5 and have no text limits; a negative persisted rating can break the admin's string-repeat rendering. Contact input is interpolated into HTML email without escaping. Unauthenticated discount validation also acts as a code/balance oracle. [Review submission][review-actions], [review moderation][reviews-page], [contact action][contact-actions], [waitlist action][waitlist-action], [discount API][discount-api], [tracking action][track-actions].

**Fix:** enforce shared schemas, payload limits, per-operation rate limits, and meaningful abuse monitoring. Escape email values or use an escaping template system. Bound ratings and content; consider verified-purchase labels separately from moderation. Keep tracking responses minimal and protect private detail with a secret or verified identity. Deployment-level protections remain to be checked.

### F38 P2 Waitlist status is cosmetic rather than a lifecycle

Waitlist submission only checks for `@`, does not normalize the email, and has no verification or unsubscribe path. The admin always displays Active, ignoring stored `isVerified` and `unsubscribed` fields. Campaign and verification models do not have a corresponding application workflow. [Waitlist submission][waitlist-action], [waitlist client][waitlist-client], [schema][schema].

**Fix:** show actual subscriber state and implement verification, unsubscribe, suppression, and campaign delivery status if launch mail is needed. Do not label every stored address as active or verified. Sending a campaign remains a separate authorized action.

## Performance release quality and maintenance

### F39 P2 Images and list fetching create avoidable payload growth

The uploader embeds compressed base64 images into database records, and public/admin pages pass these records to clients. A URL-based upload helper exists but has no callers in the application. Several lists load all records and relations, and recommendations fetch all published products before filtering. Browser image sizing/optimization is inconsistent. These are structural scaling risks; page speed and production traffic were not benchmarked. ### F40 P1 Database migrations do not reproduce the current schema

The current order schema includes `sentToInfinidis`, but the only committed SQL migration does not. Check environment pass-through: root build configuration lists Clerk/database variables but omits email, blob, and courier settings. [Build task configuration][turbo].

### F41 P1 Automated checks do not protect the selling workflows

Only four focused unit tests run manually; the web package has no test script connecting them to the root test task. No checked-in CI workflow or end-to-end/integration suite covers purchase, authorization, inventory races, cancellation, dispatch, or collected-money reporting. **Fix:** wire existing tests into scripts and CI, then add business-invariant integration tests and a compact browser suite. Resolve meaningful lint errors as touched areas are repaired and finish with a green baseline. Protect release checks and use a staging database with disposable data and mocked email/courier delivery.

### F42 P2 Search metadata and private-page indexing need completion

Product detail has no product-specific metadata or product structured data. Global social metadata references `/og-image.jpg`, which is absent from public assets. Robots omits account, receipt, and tracking routes from its exclusions; private-page `noindex` is not defined. ### F43 P1 The mobile builder hides product names and step meaning

**Fix:** use a mobile card with image and readable name/price on one row and quantity controls below or beside them with reserved space. Keep minimum quantities, full prices, and the selected configuration readable at 360px and 390px.

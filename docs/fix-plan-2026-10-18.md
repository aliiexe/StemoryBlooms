# Stemory Blooms implementation plan

18 October 2026

Repair the selling and fulfillment foundation first, then rebuild the admin workflows around reliable data, and finish the customer experience. Retain the current Next.js, Drizzle, Clerk, and shared CSS stack. A framework rewrite would add migration risk without addressing the business rules causing most defects.

The [project audit][audit] contains 43 findings and source references, including observations from authenticated desktop checks and selected mobile flows. This plan translates them into seven delivery phases. Implementation is underway. The first security, checkout, and admin batch is implemented locally; see the [release notes and verification limits](security-checkout-release.md). Deployment, historical reconciliation, hosted staging checks, and the remaining workflows below are still outstanding.

## Delivery sequence

Effort ranges are planning estimates for one experienced developer, including focused verification. They are not commitments. Allow roughly **7–12 working weeks** for the complete scope if the business rules below are resolved promptly. Data cleanup, provider approval, translations, and deeper findings from the authenticated walkthrough can change that range. The first safety release should be much smaller than the full redesign.

## Business rules to settle during implementation

These choices affect data and UI design. Use the following defaults for planning, then confirm them against the real operation before the dependent implementation.

| Decision | Proposed starting point | What depends on it |
| --- | --- | --- |
| Ready-made versus made-to-order products | Classify each product explicitly. Reserve finished units for ready-made products; reserve materials/components for made-to-order work. | Stock model, availability, production, lead times. |
| Included wrapping and cards | Preserve the existing preview's intent: base packaging is included once; any paid extras are explicit quote lines. | Builder pricing and assisted orders. |
| Order progression | New → Confirmed → In production → Ready → Shipped → Delivered. In-person handoff can finish from Ready. Cancellation, return, and refund are distinct operations. | Admin actions, tracking, stock restoration. |
| Cash and delivery charges | Show the buyer's full amount to collect. Track merchandise value and carrier charges separately for reporting. | Receipts, carrier payloads, finances. |
| Payment recognition | Keep ordered value separate from collected cash and courier remittance. Gift-card redemption is tender, separate from promotional reduction. | Finance model, profit, refunds. |
| Guest purchases and account linking | Keep guest checkout. Grant access through verified ownership or a secret receipt token; avoid relying on supplied email text alone. | Account history and privacy. |
| Currency precision | Use integer centimes for persisted money, with explicit conversion of existing whole-MAD fields. Quantities remain whole units. | Migration, all totals, expenses. |
| Staff permissions | Keep ADMIN/CUSTOMER initially; consistently enforce them. Add staff roles only if actual operations require separate catalog, fulfillment, or finance access. | Authorization and navigation. |
| Language | Keep the existing language for repairs; decide whether French or Arabic is required before expanding content and layout. | Translation, labels, search, RTL testing. |
| Returns and support promises | Publish the actual process and working contact channels; define deadlines and remedies with the business owner. | Checkout, policies, customer service. |

## Phase 0 Establish a safe verification environment

Create an isolated staging database with representative fictional customers, products, custom components, delivery zones, gift cards, and orders in every state. Give the owner a normal admin sign-in path. Route emails and courier calls to test adapters so browser verification cannot contact customers or dispatch orders. Use production configuration only for read-only comparison when necessary.

Wire the four existing tests into a package test command and a CI pipeline running lint, types, tests, build, and migration checks. Record the existing failing lint baseline, then reduce it while repairing the relevant modules. Update architecture and environment setup documentation. Verify migration drift, including the missing courier flag, before relying on a fresh database.

Extend the completed desktop and 390px spot checks to the full mobile, tablet, and desktop matrix. Reproduce the measured order-detail overflow, overlapping inventory metrics, and clipped builder names before fixing them. Capture remaining dead ends and form errors as additions to this backlog. Use keyboard interaction and a screen reader as well as pointer input.

**Acceptance criteria**

- A clean checkout can install, migrate an empty database, seed test data, and start the app from documented instructions.
- A customer account and an admin account are available for verification without bypassing authorization.
- Test email and delivery calls cannot send to real recipients or the live carrier.
- Existing unit tests run through the normal project command and CI.
- The remaining visual pass has results for every supported route, including narrow mobile screens and failure states.

## Phase 1 Protect access and make checkout trustworthy

Add authorization and input schemas to sensitive mutations, beginning with quick product edits. Choose a single source of role authority and test demotion. Replace public receipt-by-reference access with owner checks and guest access tokens. Restrict public catalog results to their intended field set and published state.

Create a shared order service used by website and assisted entry. Introduce typed catalog/custom cart lines, a validated custom selection model, and a server quote. Use trusted product names and prices, active zones, and an explicit eligibility check. The quote should contain merchandise lines, included packaging, extras, promotion, gift tender, delivery, amount due, and expiry/version information. If the quote changes, show the buyer the new amount before submission.

Within one order transaction, resolve contact identity safely, persist immutable snapshots, secure all stock, consume benefits, create the order, and enqueue downstream work. Verify conditional updates. Preserve one checkout attempt key across retries, replay the saved response for the same request, and reject changed payloads with a conflict. Generate durable order references. Enforce store mode at the service boundary. Add rate limits and complete public-input validation.

**Acceptance criteria**

- Anonymous and customer accounts cannot change products, stock, roles, settings, or finances through direct calls.
- A different customer cannot open an order's private receipt; guest tokens work and can be revoked.
- Catalog-only, custom-only, and mixed carts complete with correct recipes and card messages.
- Negative, fractional, unknown, excessive, or unavailable selections fail before database mutation.
- Two concurrent purchases for one remaining unit produce exactly one accepted purchase and one stock conflict.
- Two concurrent redemptions cannot overspend a gift balance or exceed a promo usage limit.
- Duplicate submission and a lost HTTP response produce one order and a recoverable result.
- An inactive/mismatched zone is rejected; maintenance and waitlist modes reject public checkout.
- Website and assisted ordering resolve repeat customers consistently without silently taking over another customer's order history.
- An accepted order remains successful when email, courier, or notification delivery fails.

## Phase 2 Make inventory and order changes consistent

Separate recipe editing from manufacturing, purchase, reservation, sale, cancellation, return, damage, and stock correction. Use atomic movements with actor and reason. Transactions must prevent negative balances and lost concurrent updates. Recipe edits should not silently “unmake” completed products. Remove the repeatable auto-deduction backfill from routine inventory controls.

Build one order transition service with allowed paths, history, and idempotent stock effects. All entry points, including Deliveries, use it. Archive orders rather than treating deletion as a return. Preserve the historical contact and product snapshots introduced in phase 1. Save material suppliers, model purchase costs accurately, and make stock and purchase expense commit together.

Implement durable assisted-order drafts and resume/convert if the owner needs them. Otherwise remove the placeholder custom-order page and expose custom orders as a filter over the real order workspace. Show production selections clearly in the order detail.

**Acceptance criteria**

- Two restocks preserve both quantities and both purchase expenses; a failed expense write rolls back its stock movement.
- Two cancellation requests restore inventory once. A prohibited transition changes nothing.
- Reopening a cancelled order proves availability; it cannot clamp shortages away.
- Delivered stock is restored only through the documented return/inspection operation.
- Editing a description, image, or recipe does not consume raw stock by itself.
- Stock corrections require a reason and appear in movement history with the actual actor.
- Used recipes and historical order detail remain readable after catalog changes or archival.
- Supplier selection persists and displays after reload.
- Failed inline saves restore the prior value, and successful changes update list rows and summary cards.
- Any draft can be resumed and converted once; drafts do not count as sales.

## Phase 3 Rebuild the admin around daily tasks

Use one consistent shell with a full mobile drawer, exact page titles, breadcrumbs, visible active state, and an accessible store-mode indicator. Retain the brand palette and custom-designed controls, with semantic keyboard behavior. Use compact, readable operational layouts; decoration and animation should support clarity.

### Proposed navigation

| Area | Screens |
| --- | --- |
| Overview | Today's tasks, order queues, low stock, delivery failures, pending COD reconciliation. |
| Orders | All orders, create order, drafts, production queue, order detail. Custom orders are a type/filter. |
| Catalog | Products, categories, builder components, recipe editing. |
| Inventory | Stock, movements, purchases/restocks, suppliers. |
| Delivery | Ready to dispatch, shipments, carrier errors, zones and carrier settings. |
| Customers | Customer detail, order history, notes and controlled contact updates. |
| Finance | Cash collection, carrier remittances, expenses, refunds, reporting. |
| Marketing | Promotions, gift cards, announcements, supported site content, waitlist. |
| Support | Messages, review moderation. |
| Settings | Store mode, business details, policies, staff/access, integrations. |

On mobile, use quick links to Overview, Orders, Inventory, and a complete Menu. Every area remains reachable. Keep site mode out of accidental quick-action territory: display its consequences clearly and report failures without optimistic false success.

### Screen requirements

| Screen | Required behavior |
| --- | --- |
| Overview | Prioritize actionable queues. Each metric uses the same definitions as reports and opens its matching filtered list. |
| Orders | Search by reference/name/phone, filter by fulfillment/payment/source/date, server pagination, explicit status, amount due, delivery summary, saved views, and guarded bulk actions. |
| Order detail | Immutable customer/recipient, full recipe and card text, contact actions, money breakdown, payment and fulfillment history, next valid actions, courier attempts, notes, secure receipt, archive. |
| Create order | Reuse the quote/order service, searchable products/components, visible stock, recipient separate from buyer, explicit source, zone or hand delivery, reasoned manual discount, draft, summary, and duplicate prevention. |
| Products | Search/filter/sort, clear draft/published and stock states, structured editor, media progress/error, recipe editing separated from production, preview. |
| Inventory | Search, low-stock filter, clear unit and cost labels, purchase/restock versus correction actions, supplier, movement detail, and conflict feedback. |
| Customers | Searchable profiles, verified account association where available, all channel orders, risk/internal notes, controlled edits, no exposure through public receipts. |
| Delivery | Carrier selection, ready queue, dispatch preview, reference, sync status, retry, and exception handling. |
| Marketing | Editable existing promos and gifts; real status/usage; typed content editors and publish preview; announcement scheduling with a clear timezone. |
| Support | Read/resolve queues, full message/review detail, meaningful state, and moderation without losing context. |

**Acceptance criteria**

- All supported screens are reachable through desktop and mobile navigation; no hidden group receives keyboard focus.
- Core work is usable at 360, 390, 768, 1024, and 1440px without page-level horizontal overflow. Large tables may scroll within labeled containers.
- Orders can be found by reference, customer, and phone, with shareable filters and pagination.
- Every mutation displays pending, saved, validation-error, permission-error, and conflict states as applicable, with retry and preserved inputs.
- Dialogs manage focus, close with Escape when appropriate, and restore focus; dropdowns and toggles operate entirely by keyboard.
- Primary touch actions have a practical minimum target around 44px, with visible focus and tested contrast.
- Unsupported buttons/fields are implemented or removed. No screen suggests that saved data changes something it does not control.

## Phase 4 Reconcile delivery cash and expenses

Unify dispatch around one workflow and real carrier acknowledgement. Verify the provider's current API requirements, then implement explicit timeouts, retry classification, duplicate protection, and reference storage. Process external work durably through the outbox with a supported background runner. Expose failed jobs and safe retry from admin.

Separate order fulfillment, payment collection, and carrier remittance. Record collected cash, carrier fees, owner receipts, refunds, manual adjustments, and gift-card tender. Build a shared reporting query/model used by Dashboard, Reports, and Finance, with the Africa/Casablanca business timezone and explicit date boundaries.

Customer and merchant order messages should have verified sender identity, clear amount due, delivery expectation, and secure order links. Notification status must be visible independently of order success.

**Acceptance criteria**

- Repeated dispatch requests create one carrier submission, or use a provider-supported deduplication/reconciliation path.
- A timeout does not silently mark an order shipped; the UI shows an actionable uncertain/failed state.
- Courier callbacks or polling reconcile state with a recorded history and defined conflict rules.
- Cancelled/unpaid orders do not masquerade as collected cash; remittance pending is separate from cash received.
- Dashboard, order detail, receipts, carrier amount to collect, and finance figures reconcile to the same test orders.
- Gift redemption and reversal preserve balances and are not conflated with promotional discounts.
- Worker retries survive a process restart; failed emails can be retried without creating another order.
- Buyer and merchant messages reach test destinations with the correct totals and receipt access controls.

## Phase 5 Complete the customer journey and marketing tools

Make discovery useful: categories, relevant filters/sorting, accurate stock or made-to-order badges, clear production/delivery timing, informative no-result states, and working support links. Give the mobile builder readable names/prices, a current-step label, and quantity controls that do not squeeze out the product information. Make the cart editable with current quotes, custom configuration summaries, stock warnings, and accessible controls. Checkout should clearly show amount due and service policies; simplify repeated consent controls according to actual business requirements.

Make success, tracking, and account history agree with the order lifecycle. Show “order received” versus “confirmed” accurately. Provide My Orders, verified ownership, secure receipts, and address management. Restore drafts deliberately without persisting unnecessary personal data indefinitely.

Repair gift-card form contracts and promotion rules. Add management of existing records. Connect supported content editing to actual pages, with preview and publish. Complete waitlist state, verification/unsubscribe, and campaign status if campaigns are part of the product. Move images to object storage and add proper product metadata, social imagery, sitemap refresh, and transactional noindex behavior.

**Acceptance criteria**

- A guest can find a bouquet, understand timing and total cost, buy it, retrieve confirmation, and track it without a dead end.
- Product availability and prices agree across cards, detail, cart, quote, and committed order.
- Editing/removing codes removes them from both the visible summary and submitted payload.
- Custom selections, packaging, and card message survive navigation and display correctly in order detail and receipts.
- At 360px and 390px the builder displays full readable product names, prices, minimum quantities, and the current step without clipped information.
- Gift cards can be created, edited, disabled, redeemed, and reversed with correct persistence and history.
- Every displayed promotion restriction is enforced by the server.
- A published content edit appears on its target storefront page; drafts do not appear publicly.
- My Orders is reachable, belongs to the signed-in person, and includes tracking and secure receipt links.
- Policy/support links resolve; contact and delivery promises match actual operations.
- Waitlist admin reflects real verification and suppression state; unsubscribe works before any campaign launch.
- Representative mobile pages meet performance budgets established from measurements; large base64 payloads no longer grow list responses.

## Phase 6 Verify data and release in small increments

Before changing historical data, generate a read-only discrepancy report covering negative or suspicious stock, repeat backfill effects, fulfilled/cancelled order stock movements, customer contact conflicts, gift-card usage, promo counts, expenses, and courier remittances. Review proposed corrections against available records. Apply approved corrections transactionally with before/after records and a recovery path. Do not infer missing accounting history from current stock alone.

Verify a database restore, migration upgrade, deployment configuration, background execution, and error reporting. Add monitoring for failed checkout, stock conflicts, abandoned attempts, notification backlog, dispatch errors, and unreconciled COD. Use staged releases: access/checkout safety, lifecycle/stock, admin workflows, delivery/money, then storefront/marketing polish. Retain old paths only as controlled redirects until replacements are verified.

**Release gate**

- All four P0 findings are resolved and have regression coverage.
- Every P1 finding in the released scope has passed its acceptance tests; unresolved items are explicitly tracked with restricted exposure where needed.
- Lint, types, tests, production build, and migration checks pass through normal commands in CI.
- The compact browser suite covers guest/catalog checkout, custom/mixed checkout, retries, receipt privacy, admin authorization, cancellation, stock correction, dispatch failure/retry, and collected-money reports.
- Owner walkthrough completes one realistic day: create product, purchase stock, manufacture if relevant, create an assisted order, fulfill website/custom orders, hand off delivery, reconcile payment, handle cancellation/return, update marketing, and resolve support.
- Mobile and keyboard verification covers the core screens and their real error/empty states.
- Existing-data discrepancies have an agreed resolution, and backups/rollback are verified before migrations or corrections.

## First implementation batch

Begin with a narrow, reviewable safety batch: protect quick product edits, secure receipts, enforce strict item schemas, repair custom cart identity, enforce active zones and site mode, and add regression coverage for those paths. Follow immediately with the shared transactional order service, stock/benefit concurrency checks, durable idempotency, and notification isolation. This provides a useful safety release while the broader admin work is designed.

Track each audit ID with an owner, implementation change, test evidence, and final status. An item is complete only when its UI, server behavior, and stored data agree.
